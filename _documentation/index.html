—OVERVIEW

What this actually builds

The car drives itself around an unmapped space and comes back with a map. Four things have to cooperate: SLAM Toolbox builds the map from laser scans, an EKF keeps odom → base_link honest, Nav2 plans and follows paths, and a frontier explorer keeps handing Nav2 somewhere new to go.

Start with the official build guide

This page picks up where the upstream documentation ends. It assumes you have already built the car, flashed the VESC and installed the driver stack by following the official RoboRacer (formerly F1TENTH) documentation — that is the complete, step-by-step setup guide, and nothing here replaces it.

Note the rebrand: f1tenth.org now redirects to roboracer.ai. The docs still live under the f1tenth.readthedocs.io domain.

Frontier explorer

Finds the boundary between mapped and unknown space, picks the nearest reachable one, sends it as a NavigateToPose goal.

SLAM Toolbox

Owns /map and map → odom. No AMCL, no map_server — there is no prior map to localise against.

EKF fusion

Wheel encoders give forward speed, the VESC gyro gives yaw rate. Together they beat either alone on an Ackermann chassis.

Ackermann bridge

Nav2 speaks Twist; the car steers. A bicycle-model bridge converts, clamps, and acts as watchdog.

01PREFLIGHT

Confirm what the car already has

Worth checking before installing anything — on the reference car, a directory called ~/f1tenth_ws/src/Nav2 turned out to hold only YAML config. Nav2 itself was never installed. 

# the four support packages below ship as slam_toolbox dependencies —
# seeing them does NOT mean the navigation stack is present
ros2 pkg list | grep nav2
# nav2_common  nav2_map_server  nav2_msgs  nav2_util   <- not enough

ls /dev/sensors/          # expect: vesc -> ../ttyACM0
ping -c3 192.168.0.10     # the LiDAR is on its own wired subnet

A working stack needs bt_navigator, controller_server, planner_server, behavior_server, lifecycle_manager and costmap_2d. If those are missing, nothing can navigate no matter how good the config is.

02INSTALL

Install Nav2 and robot_localization

sudo apt update
sudo apt install -y ros-humble-navigation2 ros-humble-nav2-bringup \
                    ros-humble-robot-localization

# should now report ~30 packages
ros2 pkg list | grep -c nav2
Humble renamed a server

Config written for Galactic or earlier uses recoveries_server with nav2_recoveries/* plugins. Humble calls it behavior_server with nav2_behaviors/*. The old names do not error — they simply never load, and you get a stack with no recovery behaviours at all.

03TRANSPORT

Fix DDS before you debug anything else

This step is unglamorous and it cost the most time. Two separate transport faults each made costmaps silently fail to arrive, which looks exactly like a Nav2 misconfiguration and is not one.

Stale shared-memory segments

If anything ever ran ROS as root, /dev/shm keeps root-owned fastrtps_* files that your user cannot lock. The tell is open_and_lock_file failed on startup. 

sudo rm -f /dev/shm/fastrtps_*    # with the stack stopped

Foreign participants on a shared network

On a busy lab LAN, another machine's DDS traffic reaches this one and every single node — including static_transform_publisher, which subscribes to nothing — starts printing sequence size exceeds remaining buffer. Large topics like the costmaps never arrive at all.

The diagnostic that matters

If the error appears in nodes that have no business receiving big messages, it is discovery traffic, not your payload. Chasing message size will waste your afternoon — as it did here. 

# everything runs on the car, so keep DDS on loopback and off domain 0
export ROS_DOMAIN_ID=42
export ROS_LOCALHOST_ONLY=1

run_exploration.sh sets both. The trade-off is that off-board tools stop seeing topics, so run RViz on the car over ssh -Y.

Socket buffers

Costmaps exceed the 64 kB UDP datagram limit and must fragment. Worth raising regardless of the above: 

sudo tee /etc/sysctl.d/60-ros2-large-messages.conf <<'EOF'
net.core.rmem_max=2147483647
net.core.rmem_default=2147483647
net.core.wmem_max=2147483647
net.core.wmem_default=2147483647
net.ipv4.ipfrag_time=3
net.ipv4.ipfrag_high_thresh=134217728
EOF
sudo sysctl -p /etc/sysctl.d/60-ros2-large-messages.conf
04ODOMETRY

Fuse the wheel odometry with the VESC gyro

vesc_to_odom derives heading by integrating the commanded steering angle through a bicycle model. That is open loop: it knows nothing about tyre slip, servo lag or steering trim, so yaw drifts badly. The VESC's onboard gyro measures yaw rate directly. Fusing them gives SLAM Toolbox a much steadier frame to scan-match against.

The raw IMU topic is not usable as published

vesc_driver.cpp copies packet fields into a sensor_msgs/Imu verbatim. Three things break robot_localization, and none of them announce themselves:

ProblemAs publishedConsequence
Empty frameframe_id: ''No TF lookup; every message dropped
Zero covarianceall 0.0Read as infinite certainty; filter degenerates
Non-SI unitsgyro °/s, accel gSilently wrong by 57× and 9.8×

The giveaway for units is that a stationary car reports linear_acceleration.z ≈ 1.01 — that is 1 g, not 9.81 m/s². vesc_imu_conditioner.py fixes all three and republishes on /imu/data, and also removes the gyro's zero-rate bias.

Keep the car still at launch

Bias is measured from the first 200 samples (~4 s). Nothing is published until that finishes, which usefully makes Nav2 wait rather than start on a biased gyro. On the reference car the z-bias came out at 0.0057 rad/s.

What gets fused

Only velocities, never absolute pose. In the odom frame the EKF is a dead-reckoner; SLAM corrects accumulated drift through map → odom.

SourceFusedWhy
/odomforward velocity vxWheel encoders measure speed well
/imu/datayaw rate vyawGyro measures rotation well
/imu/dataorientation — excludedUnreferenced AHRS; a jump would tear the map
/imu/dataaccel — excludedRC chassis vibration swamps the signal
One publisher per transform

The EKF now owns odom → base_link, so vesc_to_odom must stop broadcasting it. That is the single change in vesc_ekf.yaml — publish_tf: false. Two publishers on one transform makes TF non-deterministic and the map tears.

05KINEMATICS

Teach Nav2 that the car cannot spin

Nav2 assumes a differential base unless told otherwise. An Ackermann car has two hard constraints it will otherwise violate.

No rotation in place

use_rotate_to_heading: false is not optional. Left on, the controller commands a pure spin the car physically cannot execute, and the goal times out with the car sitting perfectly still. For the same reason the behaviour tree uses BackUp and never Spin.

A footprint that matches the car

base_link sits at the rear axle, not the car's centre — the LiDAR's static transform puts it 0.27 m forward. A symmetric [±0.35, ±0.20] box therefore claims 0.35 m of car behind the rear axle where none exists, and 0.20 m half-width on a car whose half-width is 0.15 m. That inflates the inscribed radius by 5 cm and puts the footprint in permanent collision beside any wall. The corrected box is [[0.45, 0.15], [0.45, -0.15], [-0.12, -0.15], [-0.12, 0.15]].

A real minimum turning radius

Servo calibration gives the limit. From vesc.yaml, servo = -1.2135·δ + 0.5304 clamped to [0.15, 0.85], so usable steering is about −0.263 to +0.313 rad. Taking 0.26 rad as the symmetric limit: 

R_min = wheelbase / tan(δ_max) = 0.25 / tan(0.26) ≈ 0.94 m
A parameter that does nothing

Humble's regulated pure pursuit controller has no min_turning_radius parameter. Config inherited from older Nav2 often sets it, along with max_linear_vel and max_linear_accel. Verify with ros2 param list /controller_server — anything absent there is being ignored, and any limit you think it enforces is not enforced.

The kinematic clamp therefore lives downstream in cmd_vel_to_ackermann.py, where max_steering_angle bounds steering for real.

The bridge does three jobs

It publishes continuously at 20 Hz rather than only on each /cmd_vel, which matters more than it sounds:

  1. Primes odometry. vesc_to_odom only emits /odom while servo commands flow. With /drive silent the transform vanishes and Nav2's costmaps come up blind — no TF means no scan raytracing, which means no obstacles, which means the car drives into walls.
  2. Feeds the mux. ackermann_mux drops any input silent for 0.2 s.
  3. Acts as watchdog. If Nav2 stops publishing, commands go stale and the bridge commands zero. Without it the VESC holds the last speed forever and the car drives off on its own.

The motor has a minimum speed

A VESC will not start a sensorless motor at very low eRPM. On the reference car Nav2 settled on 0.19 m/s — about 880 eRPM — and the VESC reported current_motor: -0.03 A with speed: 0.0 and fault_code: 0. The command was accepted, no current flowed, and the car never moved. Nav2 then aborted on the progress checker, which reads like a planning bug and is really a motor threshold.

Two changes together fix it:

  • use_cost_regulated_linear_velocity_scaling: false — with 0.35 m inflation indoors, cost is high nearly everywhere, and this was what dragged the request down to 0.19 m/s. Curvature regulation stays on; that is the one an Ackermann car needs.
  • min_move_speed in the bridge raises any non-zero request up to a speed the motor will actually start at. Zero stays exactly zero — a stop must never become motion.
Calibrate, don't guess

The threshold is per-car: it depends on motor, gearing, tyres and floor. Run speed_threshold.py with only the hardware up — it ramps the command in short bursts and reports the lowest speed that actually turned the wheels. Feed that into min_move_speed, regulated_linear_scaling_min_speed and min_approach_linear_velocity. The defaults here (0.55 m/s) are a starting point, not a measurement.

06STEERING

Trim the steering so zero means straight

With a zero steering command the car must run straight. If it arcs, the commanded centre does not match the mechanical centre, and SLAM has to absorb the error as heading drift. The knob is steering_angle_to_servo_offset in the VESC config: 

servo = steering_angle_to_servo_gain * delta + steering_angle_to_servo_offset
      = -1.2135 * delta + offset          # this car

The offset is the servo value meaning wheels straight. It is a mechanical property of the individual car and changes whenever the linkage, servo horn or tie rods are touched, so the stock value is only a guess.

Direction

Higher offset steers RIGHT, lower steers LEFT. It follows straight from the negative gain. Trust the equation: an attempt to derive this empirically here produced the opposite answer and several wasted iterations, because the measurements were taken while a servo cable was intermittently seated.

The offset is bounded by the servo clamps

servo_min / servo_max bound the offset, because full lock either way must still fit inside them: 

left  lock: offset - 1.2135 * delta_max >= servo_min
right lock: offset + 1.2135 * delta_max <= servo_max

# stock 0.15 / 0.85 with delta_max 0.26 rad gives:
0.4655 <= offset <= 0.5345
Outside the window, a lock silently clamps

Set the offset above the ceiling and full right lock is truncated; below the floor and left lock goes. Nothing warns you — the car just loses steering travel on one side. On the reference car an offset of 0.5420 clipped right lock exactly this way. Always compute both locks after changing the offset.

Procedure

  1. Clear a straight run of about 3 m. Shorter is not enough: over 0.25 m a 4° error moves the nose only ~2 cm, which is lost in tyre scrub.
  2. safe_drive.sh 0.4 2.0 — drives with steering commanded to exactly 0, and refuses to run if there is not room.
  3. Watch which way it arcs. Veers left → raise the offset; veers right → lower it.
  4. set_offset.sh <value> and repeat. The driver reads the offset once at startup, so this restarts it; ros2 param set alone would report the new value while the car kept behaving the old way.

For a number rather than an eyeball call, steering_trim.py reads the conditioned gyro and inverts the bicycle model, delta_err = atan(wheelbase * yaw_rate / speed). It needs only ~1 m per pass. It refuses to fall back to /odom, whose yaw rate is derived from the servo command — measuring trim from that is circular.

When the offset cannot reach

If the car still veers at the window's edge, the clamps are the limit, not the servo. servo_min / servo_max are conservative software values; most servos travel further. servo_limit_test.sh high steps the commanded position outward in increments so you can see where the wheels actually stop.

Do not park on a stalled servo

Past its mechanical stop the servo stalls, drawing current continuously until it overheats — and temp_motor reads 0.0 on this VESC, so nothing warns you. Widen the clamps only as far as the measured travel, then back off a little.

The reference car ended at offset 0.58 with servo_max raised to 0.90 (full right lock needs 0.8955). That is 4.4° of right bias past stock — a large trim, and a sign the linkage itself is off true. Correcting it mechanically, at the servo horn or tie rod, gives the range back and costs no steering travel.

07LIDAR

Rule out a LiDAR self-hit — properly

If the LiDAR can see part of the car, that hardware is marked as an obstacle that travels with the robot, painting a trail it can never escape. It is worth checking. It is also very easy to diagnose wrongly, so the method matters more than the check.

Test on open floor, never in a tight spot

With the car boxed in, on-car hardware and the surrounding walls are indistinguishable — both sit close and both stay put. On this car that produced a confident, wrong diagnosis: close returns at +95°…+135° persisted across a 139° rotation, which looked conclusive and was coincidence. The car had walls on several sides in both positions.

Move the car to open floor with at least a metre clear all round. There, anything still returning under ~0.8 m is on the car by definition. 

# stock sensors config — you need the FULL 270 deg view for this test
ros2 launch f1tenth_stack bringup_launch.py \
    vesc_config:=~/f1tenth_exploration/vesc_ekf.yaml
python3 ~/f1tenth_exploration/mount_probe.py

mount_probe.py converts every close return into base_link coordinates and clusters them, so it names the location of anything it finds. On the reference car the verdict was "No returns under 0.35 m — nothing near the sensor": no self-hit, and no masking needed.

Masking hides real obstacles

Trimming angle_max does silence detected collision ahead! — but it silences it just as effectively when the obstacle is a genuine wall. Nav2 then drives into the sector it can no longer see. Masking is a last resort after mount_probe.py has positively identified on-car hardware on open floor; the real fix is remounting the LiDAR above the obstruction. When the test comes back clean, as it did here, suspect the footprint and inflation instead.

For reference, this car's mount is base_link → laser = (0.27, 0.00, 0.11) with identity rotation, hardcoded in bringup_launch.py — there is no URDF in the workspace. At 11 cm the scan plane is low enough to clip a tall Jetson or battery on other builds, so the test is worth running on any new car.

08LAUNCH

Bring it up

cd ~/f1tenth_exploration

./run_exploration.sh --no-drive   # stack only, car stays put
./run_exploration.sh              # full autonomous run
./run_exploration.sh --kill       # stop, leaving the car stopped

tmux attach -t explore            # bringup · stack · explorer · record
Before the car moves

Flat enclosed area. No stairs, drop-offs, cables to snag or anything fragile within reach. Stay with the car and hold the joystick — its mux priority of 100 against Nav2's 10 means the deadman button overrides Nav2 completely, and that is your only e-stop.

Speed is capped independently in two places: desired_linear_vel (0.5 m/s) in nav2_params.yaml and max_speed (0.6 m/s) in the bridge. Lower both to slow the car; lowering one alone is not a cap.

Always run --no-drive first on a stack you have changed, and only start the explorer once the checks below pass.

These are the exact checks used on the reference car, with the values it returned.

Check costmaps with a subscriber, not the CLI

ros2 topic hz on an OccupancyGrid reports sequence size exceeds remaining buffer even when the topic is perfectly healthy. Subscribe and count cells instead — a local costmap reading 0% occupied while the car sits in a room is the blind-costmap failure, and it is the one that drives into walls.

10MAP

Save the map

The explorer stops on its own once no reachable frontier remains. Save before tearing anything down — the map lives only in SLAM Toolbox's memory.

mkdir -p ~/maps
ros2 run nav2_map_server map_saver_cli -f ~/maps/explored_map
# writes explored_map.pgm + explored_map.yaml

To navigate that map later rather than rebuild it, swap SLAM Toolbox for map_server plus AMCL — and set AMCL's robot_model_type appropriately for a steered chassis.

11DEBUG

When it misbehaves

Trace the chain, do not guess

Most of the hard faults here were found by walking the command path one stage at a time and asking what each stage proves. When the steering died, /commands/servo/position carried exactly the right values — but that is the topic the driver SUBSCRIBES to, so it proved nothing about the VESC. Reading /sensors/core back (live telemetry, fault_code: 0) proved the serial link worked in both directions, which placed the fault downstream of the VESC and led straight to an unseated servo cable. Check what a signal actually demonstrates before concluding from it.
